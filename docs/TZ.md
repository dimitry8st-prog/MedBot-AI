## 2. Назначение и цели создания системы

### 2.1. Основные проблемы

**Проблема 1: Информационная перегрузка**
- Врачи не успевают отслеживать обновления протоколов
- Сложно находить релевантную информацию в больших документах

**Проблема 2: Низкая доступность экспертизы**
- Не всегда есть возможность проконсультироваться с коллегами
- Дефицит узких специалистов в регионах

**Проблема 3: Отсутствие критической оценки источников**
- Сложно оценить уровень доказательности утверждений
- Много противоречивой информации в интернете

### 2.2. Решение

**MedBot AI предоставляет:**
- Семантический поиск по медицинской базе знаний (RAG)
- AI-анализ симптомов с обоснованием
- Автоматическую оценку доказательности источников
- Быстрый доступ через Web и Telegram

### 2.3. Цели системы

**Основные:**
1. Сократить время поиска релевантной медицинской информации в 5+ раз
2. Обеспечить прозрачность источников и уровня доказательности
3. Предоставить AI-ассистента, доступного 24/7

**Дополнительные:**
1. Снизить когнитивную нагрузку на врачей
2. Улучшить качество обучения студентов
3. Стандартизировать доступ к актуальным протоколам

### 2.4. Границы системы

**Система НЕ:**
- Не ставит диагнозы (только информационная поддержка)
- Не заменяет врача
- Не назначает лечение
- Не работает с персональными данными пациентов (хранение ФИО, историй болезней)

**Дисклеймер (обязательный):**
> "MedBot AI предоставляет информационную поддержку и не заменяет консультацию врача. Все решения принимаются медицинским специалистом."

## 3. Требования к системе

### 3.1. Требования к функциональности

#### 3.1.1. RAG Engine (ядро системы)

**FR-001: Загрузка документов**
- Система должна поддерживать загрузку документов в форматах: PDF, HTML, DOCX
- Автоматическое извлечение текста и метаданных
- Валидация формата и целостности

**FR-002: Индексация документов**
- Разбиение документов на семантические чанки (размер: 500–1000 токенов)
- Векторизация через embedding model (multilingual-e5-large)
- Сохранение в ChromaDB с метаданными

**FR-003: Семантический поиск**
- Вход: текстовый запрос на естественном языке (русский/английский)
- Выход: топ-5 релевантных фрагментов документов
- Метрика: similarity score (cosine similarity)
- Время отклика: < 2 секунды

**FR-004: Reranking результатов**
- Переранжирование топ-5 по релевантности контексту запроса
- Использование cross-encoder модели
- Итоговый топ-3 подается в LLM

#### 3.1.2. Symptom Analyzer (анализ симптомов)

**FR-010: Структурированный сбор анамнеза**
- Диалоговый интерфейс для уточнения симптомов
- Основные вопросы: жалобы, длительность, сопутствующие факторы
- Возможность загрузки результатов анализов (текст/изображение)

**FR-011: Генерация дифференциальных диагнозов**
- Вход: структурированный анамнез
- Обработка: поиск в RAG + анализ LLM
- Выход: 3–5 возможных диагнозов с вероятностью и обоснованием

**FR-012: Обоснование диагнозов**
- Для каждого диагноза указывать:
  - Соответствие симптомам (%)
  - Уровень доказательности источника (A/B/C/D)
  - Ссылки на протоколы/исследования

**FR-013: Рекомендации по обследованию**
- Список необходимых анализов/исследований
- Критерии дифференциальной диагностики
- **Обязательно:** напоминание о необходимости консультации врача

#### 3.1.3. Evidence Evaluator (оценка доказательности)

**FR-020: Классификация источников**
Уровни доказательности:
- **A** — Систематические обзоры, мета-анализы, RCT (рандомизированные контролируемые исследования)
- **B** — Когортные исследования, проспективные исследования
- **C** — Исследования случай-контроль, ретроспективные исследования
- **D** — Мнение экспертов, клинические случаи, серии случаев
- **E** — Маркетинг, недоказанные утверждения, анекдотические свидетельства

**FR-021: Автоматическая оценка**
- При загрузке документа в RAG — автоматическое определение уровня
- Анализ метаданных: тип публикации, журнал, методология
- Ручная модерация администратором (override)

**FR-022: Отображение уровня**
- В результатах поиска — индикатор уровня доказательности
- В ответах AI — явное указание источника и уровня
- Фильтрация результатов по уровню (только A+B, все уровни)

#### 3.1.4. Multimodal Processor (обработка изображений)

**FR-030: OCR текста**
- Распознавание текста на изображениях анализов (русский/английский)
- Поддержка форматов: JPG, PNG, PDF (одностраничный)
- Извлечение структурированных данных (ключ-значение)

**FR-031: Анализ медицинских изображений**
- Описание рентгеновских снимков через multimodal LLM
- **Важно:** только описательное заключение, без диагноза
- Указание на возможные патологические изменения

**FR-032: Извлечение данных из PDF**
- Парсинг таблиц из медицинских документов
- Извлечение результатов анализов в структурированном виде

#### 3.1.5. Protocol Search (поиск протоколов)

**FR-040: Полнотекстовый поиск**
- Поиск по ключевым словам в названиях и тексте протоколов
- Поддержка морфологии (врач → врачи → врачом)

**FR-041: Фильтрация**
Фильтры:
- Нозология (заболевание)
- Специальность (хирургия, терапия и т.д.)
- Год публикации
- Источник (Минздрав, профессиональное сообщество)

**FR-042: Просмотр протокола**
- Полный текст документа
- Оглавление с якорными ссылками
- Возможность скачать (PDF)

#### 3.1.6. Analytics Service (аналитика)

**FR-050: Личная статистика пользователя**
- Количество запросов (всего, по типам)
- Топ-10 частых запросов
- История поиска (последние 50)

**FR-051: Системная аналитика (для администратора)**
- Общее количество пользователей
- Активные пользователи (DAU, MAU)
- Популярные запросы (топ-20)
- Популярные протоколы
- Средняя оценка ответов (обратная связь)

**FR-052: Обратная связь**
- Оценка ответа (👍 / 👎)
- Комментарий пользователя (опционально)
- Агрегация в аналитике

#### 3.1.7. Управление пользователями

**FR-060: Регистрация**
- Email + пароль (минимум 8 символов)
- Подтверждение email (опционально для MVP)
- Согласие на обработку данных (152-ФЗ)

**FR-061: Аутентификация**
- JWT токены (access token — 1 час, refresh token — 7 дней)
- Logout (инвалидация токена)

**FR-062: Роли**
- **Пользователь** — базовый доступ (поиск, анализ)
- **Администратор** — управление базой знаний, просмотр аналитики

**FR-063: Профиль**
- Редактирование данных (email, пароль)
- Настройки (язык интерфейса — русский/английский)

### 3.3. Требования к API

#### API-001: Базовые принципы
- Стиль: RESTful
- Формат: JSON
- Версионирование: `/api/v1/...`
- Документация: OpenAPI 3.0 (Swagger UI)

#### API-002: Аутентификация
- Метод: JWT Bearer Token
- Header: `Authorization: Bearer <token>`
- Refresh механизм: `/api/v1/auth/refresh`

#### API-003: Основные endpoints

**Аутентификация:**
```
POST /api/v1/auth/register
POST /api/v1/auth/login
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
```

**Поиск:**
```
POST /api/v1/search
  Body: { "query": "string", "filters": {...} }
  Response: { "answer": "string", "sources": [...], "evidence_level": "A" }
```

**Анализ симптомов:**
```
POST /api/v1/analyze/symptoms
  Body: { "symptoms": {...}, "duration": "string", ... }
  Response: { "diagnoses": [...], "recommendations": [...] }
```

**Протоколы:**
```
GET /api/v1/protocols?search=...&specialty=...&year=...
GET /api/v1/protocols/{id}
```

**Загрузка документов (admin):**
```
POST /api/v1/documents/upload
  Content-Type: multipart/form-data
  Fields: file, metadata (JSON)
```

**Аналитика:**
```
GET /api/v1/analytics/user
GET /api/v1/analytics/system (admin)
```

**Обратная связь:**
```
POST /api/v1/feedback
  Body: { "query_id": "uuid", "rating": 1/-1, "comment": "string" }
```

#### API-004: Обработка ошибок
Стандартные HTTP коды:
- 200 OK — успех
- 201 Created — создан ресурс
- 400 Bad Request — некорректный запрос
- 401 Unauthorized — не авторизован
- 403 Forbidden — недостаточно прав
- 404 Not Found — ресурс не найден
- 429 Too Many Requests — превышен rate limit
- 500 Internal Server Error — ошибка сервера

Формат ошибки:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Описание ошибки на русском",
    "details": {...}
  }
}
```

#### API-005: Rate Limiting
- Неавторизованные: 10 запросов/минуту
- Авторизованные пользователи: 60 запросов/минуту
- Администраторы: 300 запросов/минуту

### 3.4. Требования к производительности

**PERF-001: Latency**
- Поиск (RAG): < 3 секунды (p95)
- Анализ симптомов: < 5 секунд (p95)
- OCR изображения: < 10 секунд (p95)
- Загрузка страницы Web UI: < 2 секунды (FCP)

**PERF-002: Throughput**
- Одновременные пользователи: минимум 50
- Запросов в секунду (RPS): минимум 10

**PERF-003: База знаний**
- Количество документов: 50–100 (MVP), масштабируется до 1000+
- Размер векторной БД: до 5GB (MVP)

### 3.5. Требования к надежности

**REL-001: Доступность**
- Uptime: 99% (допустимо ~7 часов простоя в месяц для MVP)
- Планируемое обслуживание: не более 2 часов/неделю

**REL-002: Отказоустойчивость**
- Fallback на Claude API при недоступности GigaChat
- Graceful degradation: если ChromaDB недоступен → fulltext search по PostgreSQL
- Автоматический retry для API запросов (3 попытки с exponential backoff)

**REL-003: Мониторинг**
- Логирование всех ошибок (уровень ERROR и выше)
- Health check endpoint: `/api/v1/health`
- Алерты при критических ошибках (опционально для MVP)

### 3.6. Требования к безопасности

**SEC-001: Аутентификация и авторизация**
- Хэширование паролей: bcrypt (cost factor 12)
- JWT secret: минимум 256 бит, из переменных окружения
- HTTPS обязательно для production

**SEC-002: Защита данных**
- Соответствие 152-ФЗ:
  - Согласие пользователя на обработку данных
  - Анонимизация в аналитике (без email/ФИО)
  - Право на удаление данных (по запросу)
- Не хранить персональные данные пациентов (ФИО, истории болезней)

**SEC-003: Rate Limiting**
- Защита от DDoS: Redis-based rate limiting
- Блокировка IP при превышении лимита (временная, 1 час)

**SEC-004: Валидация входных данных**
- Sanitization всех текстовых полей
- Проверка типов и форматов (Pydantic схемы)
- Ограничение размера файлов: максимум 10MB

**SEC-005: API Security**
- CORS: только разрешенные домены
- Content-Type validation
- Защита от SQL injection (использование ORM — SQLAlchemy)

**SEC-006: Логирование**
- Не логировать чувствительные данные (пароли, токены)
- Логировать попытки доступа (успешные и неуспешные)

### 3.7. Требования к масштабируемости

**SCALE-001: Горизонтальное масштабирование**
- Stateless API (можно запустить несколько инстансов FastAPI)
- Shared state в Redis/PostgreSQL (не в памяти процесса)

**SCALE-002: Оптимизация запросов**
- Кэширование частых запросов в Redis (TTL: 1 час)
- Пагинация для списков (page size: 20)
- Индексы в PostgreSQL на часто запрашиваемые поля

**SCALE-003: Векторная БД**
- ChromaDB должна поддерживать до 100k документов (будущее масштабирование)
- Batch индексация (не по одному документу)

## 10. Словарь терминов

**RAG (Retrieval-Augmented Generation)** — подход к генерации текста, при котором LLM использует внешнюю базу знаний (retrieval) для создания ответа.

**Embedding** — векторное представление текста (числовой массив), используемое для семантического поиска.

**ChromaDB** — open-source векторная база данных для хранения и поиска эмбеддингов.

**LLM (Large Language Model)** — большая языковая модель (GigaChat, Claude, GPT).

**Дифференциальная диагностика** — процесс различения заболеваний со схожими симптомами.

**Уровень доказательности** — классификация медицинских источников по качеству доказательств (A/B/C/D).

**JWT (JSON Web Token)** — стандарт токенов для аутентификации в API.

**OCR (Optical Character Recognition)** — оптическое распознавание символов (текста на изображениях).

**Multimodal LLM** — языковая модель, способная обрабатывать не только текст, но и изображения.

**Precision@k** — метрика качества поиска: доля релевантных документов в топ-k результатов.

**p95 (95th percentile)** — значение метрики, которое не превышается в 95% случаев.
