## Принципы работы

### 1. Фокус на ценность для пользователя

**Целевая аудитория:**
- Врачи общей практики (терапевты, педиатры) — 60%
- Узкие специалисты (кардиологи, неврологи, хирурги) — 30%
- Медицинские администраторы — 10%

**Ключевые боли:**
- Долгий поиск актуальных клинических рекомендаций (5-15 минут на запрос)
- Сложность дифференциальной диагностики (особенно редкие состояния)
- Отсутствие быстрого доступа к уровню доказательности методов
- Необходимость держать в голове протоколы по 20+ нозологиям

**Value proposition:**
- RAG-поиск по протоколам: 30 секунд вместо 10 минут
- AI-ассистент для дифференциальной диагностики
- Всегда актуальные рекомендации с указанием источника и уровня доказательности

### 2. Итеративная разработка

**MVP (Minimum Viable Product) — 1 месяц:**
- Telegram-бот с базовой авторизацией
- RAG-поиск по топ-20 клиническим рекомендациям (кардиология, неврология, терапия)
- История запросов
- Простой UI: query → результаты с источниками

**MLP (Minimum Lovable Product) — 3 месяца:**
- MVP +
- Symptom Analyzer (дифференциальная диагностика через GigaChat)
- Web-интерфейс (React)
- Расширенная база знаний (100+ документов)
- Фильтры по специальности, уровню доказательности

**Full Product — 6 месяцев:**
- MLP +
- Evidence Evaluator (оценка медицинских утверждений)
- Multimodal (OCR для анализов, рентгенограмм)
- Аналитика использования
- API для сторонних разработчиков

### 3. Архитектурные приоритеты

**Приоритет 1: Надежность**
- Fallback на Claude API при недоступности GigaChat
- Graceful degradation (если RAG не находит документы — честное "не знаю")
- Всегда указывать источник и disclaimers

**Приоритет 2: Качество RAG**
- Медицинская иерархия знаний (КР Минздрав > международные рекомендации)
- Динамическая актуальность (документы <2 лет получают boost)
- Cross-encoder reranking для финальной фильтрации top-3

**Приоритет 3: Скорость**
- RAG search: <1s (target: 300-500ms)
- Symptom analysis: <5s (зависит от GigaChat API)
- Embedding generation: batch processing (32 документа за раз)

**Приоритет 4: Масштабируемость**
- ChromaDB: до 10k документов (current scope)
- PostgreSQL: до 100k пользователей
- Redis: кэширование популярных запросов (TTL 1 час)

### 4. Технические решения (обоснование)

#### RAG Stack

**Embedding model: multilingual-e5-large**
- Pros: state-of-the-art для русского языка, 1024-dim, хорошо работает с медицинским текстом
- Cons: требует 2 GB RAM, CPU inference медленный (~100ms per query)
- Альтернативы: LaBSE (меньше размер, хуже качество), ruBERT (устарел)

**Vector DB: ChromaDB**
- Pros: простой, легкий, open-source, хорошая интеграция с LangChain
- Cons: не для production high-load (>100 RPS), нет кластеризации
- Альтернативы: Pinecone (платный), Qdrant (сложнее), Milvus (overkill для MVP)
- Решение: ChromaDB для MVP, миграция на Qdrant при масштабировании

**Chunking strategy: semantic (800 tokens, overlap 100)**
- Pros: сохраняет семантическую целостность, overlap предотвращает потерю контекста
- Cons: неоптимально для структурированных документов (таблицы, списки)
- Альтернативы: fixed-size (проще, но хуже качество), recursive (сложнее)

#### LLM Stack

**Primary: GigaChat API**
- Pros: российский, GDPR-compliant, понимает медицинскую терминологию РФ
- Cons: rate limits (50 req/hour на бесплатном плане), медленнее GPT-4
- Стоимость: бесплатно до 1000 req/day, далее ~5 руб/1k tokens

**Fallback: Claude API (Sonnet 4.5)**
- Pros: быстрый, качественный, хорошо следует промптам
- Cons: платный (~$3/1M input tokens, ~$15/1M output tokens)
- Use case: когда GigaChat недоступен или превышен лимит

**Prompt engineering:**
- Few-shot prompting для symptom analysis (3-5 примеров)
- Chain-of-thought для дифференциальной диагностики
- JSON mode для структурированных ответов

#### Backend Stack

**FastAPI**
- Pros: async, fast, OpenAPI docs из коробки, type hints
- Cons: менее зрелый чем Django (но для API — лучший выбор)

**PostgreSQL**
- Pros: надежный, ACID, pgvector extension (для гибридного поиска в будущем)
- Cons: требует миграции Alembic (но это стандарт)

**Redis**
- Pros: кэширование популярных запросов, сессии пользователей
- Use case: cache RAG results на 1 час (TTL), rate limiting

### 5. Монетизация (стратегия)

#### Модель freemium (рекомендуется)

**Free tier:**
- 20 запросов/день
- RAG-поиск по базовым протоколам
- История запросов (7 дней)
- Telegram-бот

**Pro tier (499 руб/месяц):**
- Unlimited запросы
- Symptom Analyzer (AI-диагностика)
- Evidence Evaluator
- Web-интерфейс
- История (90 дней)
- Приоритетная поддержка

**Enterprise tier (по запросу):**
- Custom база знаний (протоколы клиники)
- On-premise deployment
- Интеграция с МИС
- SLA 99.9%
- Обучение персонала

#### B2B модель (долгосрочная)

**Целевой сегмент:** Клиники, медицинские центры (50+ врачей)

**Ценообразование:**
- 200 руб/врач/месяц (при 10-50 врачах)
- 150 руб/врач/месяц (при 50-200 врачах)
- 100 руб/врач/месяц (при 200+ врачах)

**Дополнительно:**
- Кастомизация (250k руб единоразово)
- Интеграция с МИС (от 500k руб)
- Обучение (50k руб за 10 человек)

**Unit economics (пример):**
```
Клиника 100 врачей × 150 руб = 15k руб/мес = 180k руб/год

Расходы:
- GigaChat API: ~5k руб/мес (при 100k запросов)
- Инфраструктура: ~10k руб/мес (VDS, БД, мониторинг)
- Поддержка: 0.5 FTE (~50k руб/мес)
= 65k руб/мес = 780k руб/год

Прибыль: 180k - 780k = -600k (убыток на одной клинике)

Критическая масса: ~5 клиник (по 100 врачей) = 900k руб/год выручка → break-even
```

**Вывод:** Для B2B нужно минимум 5-10 клиентов для выхода в прибыль.

### 7. Риски и митигация

#### Технические риски

**Риск 1: Качество RAG недостаточное**
- Вероятность: Средняя
- Влияние: Критическое (пользователи не получат value)
- Митигация:
  - Cross-encoder reranking (top-10 → top-3)
  - Human-in-the-loop evaluation (ручная проверка 100 запросов)
  - Метрики: Precision@5, NDCG, MRR
  - A/B тесты разных chunking стратегий

**Риск 2: GigaChat API нестабилен**
- Вероятность: Средняя
- Влияние: Высокое (система не работает)
- Митигация:
  - Fallback на Claude API (автоматический)
  - Кэширование популярных запросов (Redis, TTL 1 час)
  - Retry logic (3 попытки с exponential backoff)
  - Мониторинг uptime (PagerDuty alerts)

**Риск 3: Медленный inference embeddings**
- Вероятность: Высокая (на CPU)
- Влияние: Среднее (1-2s latency)
- Митигация:
  - GPU inference (NVIDIA T4, ~10x speedup)
  - Batch processing (32 queries)
  - Кэширование embeddings (для частых запросов)
  - Альтернатива: OpenAI embeddings API (платно, но быстро)

#### Продуктовые риски

**Риск 4: Врачи не доверяют AI-рекомендациям**
- Вероятность: Высокая
- Влияние: Критическое (не будут использовать)
- Митигация:
  - **Всегда** показывать источник (ссылка на документ, страница)
  - Уровень доказательности (A/B/C/D/E)
  - Disclaimers: "Требуется консультация врача"
  - Позиционирование: "информационная поддержка", НЕ "замена врача"
  - Кейсы использования от практикующих врачей (testimonials)

**Риск 5: Сложная user experience**
- Вероятность: Средняя
- Влияние: Высокое (churn rate)
- Митигация:
  - Простой UI (single search bar, как Google)
  - Onboarding tutorial (3 шага)
  - Примеры запросов ("лечение гипертонии", "дифференциальный диагноз боли в груди")
  - UX тестирование с 5-10 врачами

#### Бизнес-риски

**Риск 6: Недостаточный unit economics**
- Вероятность: Средняя
- Влияние: Критическое (бизнес неприбыльный)
- Митигация:
  - Оптимизация затрат на API (кэширование, batch processing)
  - Фокус на B2B (higher LTV)
  - Увеличение конверсии free → paid (10% target)
  - Альтернативные модели монетизации (affiliate с drug databases)

**Риск 7: Регуляторные ограничения (152-ФЗ, медизделия)**
- Вероятность: Средняя
- Влияние: Высокое (запрет на использование)
- Митигация:
  - Консультация с юристами (медицинское право)
  - Позиционирование как "информационная система", НЕ "медицинское изделие"
  - Не хранить персональные данные пациентов (только метаданные запросов)
  - GDPR/152-ФЗ compliance (согласие на обработку данных, анонимизация)

### 9. Конкуренты и дифференциация

#### Прямые конкуренты

**UpToDate / DynaMed (международные):**
- Pros: огромная база знаний, высокое качество, trust
- Cons: платные ($500+/year), на английском, не адаптированы под РФ
- Дифференциация: фокус на российские протоколы, русский язык, AI-ассистент

- Pros: российские протоколы, бесплатные
- Cons: устаревший интерфейс, нет AI, плохой поиск
- Дифференциация: современный UI, RAG-поиск, AI symptom analyzer

#### Косвенные конкуренты

**Google / ChatGPT (LLM):**
- Pros: универсальные, fast, бесплатные
- Cons: галлюцинации, нет источников, не специализированы для медицины РФ
- Дифференциация: RAG (всегда источники), медицинская иерархия знаний, disclaimer

**Telegram-боты (специализированные):**
- Pros: удобный интерфейс, популярны у врачей
- Cons: ограниченный функционал, нет RAG, низкое качество
- Дифференциация: full-stack продукт (web + telegram), enterprise features

### 12. Вопросы для принятия решений

При обсуждении новых фич или архитектурных решений задавай:

1. **Impact:** Насколько это критично для пользователя? (High/Medium/Low)
2. **Effort:** Сколько времени потребуется? (в днях)
3. **Risk:** Какие риски? (Technical/Product/Business)
4. **Priority:** Когда делать? (MVP / MLP / Full Product / Backlog)
5. **Success metrics:** Как измерим успех?

**Пример:**
```
Feature: Cross-encoder reranking для RAG
```
