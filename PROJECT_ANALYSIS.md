## Executive Summary

MedBot AI — перспективная AI-платформа для медицинских специалистов с RAG-поиском по клиническим протоколам и AI-анализом симптомов. Проект находится на ранней стадии разработки (Этап 2, 50% готовности), имеет качественную документацию и продуманную архитектуру.

**Ключевые выводы:**
- ✅ Сильная техническая основа (RAG Engine на 50% готов)
- ✅ Четкая целевая аудитория (врачи РФ)
- ✅ Уникальная медицинская иерархия знаний (приоритет Минздрав РФ)
- ⚠️ Риски: качество RAG, стабильность GigaChat API, доверие врачей к AI
- 🎯 Рекомендация: фокус на MVP через Telegram-бот (1 месяц), затем B2B продажи

**Потенциал монетизации:** 500k-1M руб MRR к месяцу 12 (при 5-10 корпоративных клиентах)

## 2. SWOT-анализ

### Strengths (Сильные стороны)

1. **Уникальная медицинская иерархия знаний**
   - Приоритет российских источников (Минздрав РФ > международные)
   - Правило актуальности (2-летнее окно для boost)
   - Уровень доказательности (A-E) для каждого источника
   - **Дифференциатор:** Конкуренты (UpToDate, DynaMed) не адаптированы под РФ

2. **Качественная техническая основа**
   - State-of-the-art embeddings (multilingual-e5-large)
   - Semantic chunking (сохраняет контекст)
   - ChromaDB + PostgreSQL + Redis (масштабируемый стек)
   - Fallback на Claude API (надежность)

3. **Доменная экспертиза основателя**
   - Нейрохирург + AI-инженер = понимание потребностей врачей
   - Опыт разработки медицинских ботов
   - Нетворк в медицинской среде (доступ к early adopters)

4. **Фокус на конкретную нишу**
   - Российские врачи (25+ млн потенциальных пользователей)
   - Клиники и медицинские центры (B2B с высоким LTV)

### Weaknesses (Слабые стороны)

1. **Solo founder (один разработчик)**
   - Риск burnout
   - Медленная разработка (1 месяц на MVP vs 2 недели для команды)
   - Ограниченные возможности (backend + frontend + mobile + sales = overload)

2. **Зависимость от GigaChat API**
   - Rate limits (50 req/hour на free tier)
   - Нестабильность (молодой API, возможны downtime)
   - Стоимость при масштабировании (5 руб/1k tokens)

3. **Нет MVP (ни одного работающего продукта)**
   - Невозможно протестировать гипотезы
   - Нет обратной связи от пользователей
   - Риск "build what nobody needs"

4. **Отсутствие business development ресурсов**
   - Нет маркетолога (growth будет медленным)
   - Нет sales manager (B2B продажи сложные)
   - Ограниченный budget на рекламу

### Opportunities (Возможности)

1. **Растущий рынок MedTech в РФ**
   - Цифровизация здравоохранения (национальный проект "Здравоохранение")
   - Спрос на AI-инструменты среди врачей (особенно после COVID-19)
   - Государственное финансирование (гранты, субсидии)

2. **Низкая конкуренция в российском сегменте**
   - UpToDate/DynaMed — дорогие, на английском
   - Справочник врача — устаревший интерфейс, нет AI
   - Telegram-боты — низкое качество, нет RAG
   - **Window of opportunity:** 6-12 месяцев до появления сильных конкурентов

3. **B2B модель с высоким LTV**
   - Клиники (100+ врачей) = 180k руб/год
   - Интеграция с МИС (500k-1M руб за проект)
   - Recurring revenue (SaaS модель)

4. **Партнерства**
   - Интеграторы МИС (1С-Медицина, ЕМИАС)
   - Медицинские ассоциации (для endorsement)
   - Фармкомпании (affiliate для drug databases)

5. **Международная экспансия**
   - Адаптация для других стран СНГ (Казахстан, Узбекистан)
   - Англоязычная версия (при изменении архитектуры)

### Threats (Угрозы)

1. **Доверие врачей к AI**
   - Скептицизм (галлюцинации LLM, ошибки в диагностике)
   - Медико-правовые риски (кто несет ответственность за ошибку AI?)
   - Культурный барьер (консервативность медицинского сообщества)

2. **Регуляторные ограничения**
   - 152-ФЗ (персональные данные)
   - Закон о медицинских изделиях (если система классифицируется как медизделие)
   - GDPR (при работе с международными клиентами)
   - Риск: запрет на использование или штрафы

3. **Конкуренция со стороны крупных игроков**
   - Яндекс.Здоровье (может запустить аналог)
   - Сбер (владелец GigaChat, может сделать собственный продукт)
   - Google/ChatGPT (универсальные LLM могут заменить специализированный инструмент)

4. **Технологические риски**
   - Быстрое устаревание LLM моделей (новые модели каждые 6 месяцев)
   - Изменение pricing GigaChat API (может стать дороже)
   - Сложность масштабирования (ChromaDB не для high-load)

5. **Экономические риски**
   - Снижение бюджетов клиник (экономический кризис)
   - Низкая платежеспособность врачей (средняя зарплата ~50k руб)
   - Сложность сбора оплаты с госучреждений

## 3. Стратегия развития

### 3.1. Приоритеты на ближайший месяц (MVP)

**Цель:** Запустить работающий MVP через Telegram-бот с RAG-поиском.

**Задачи (по приоритету):**

1. **Завершить RAG Engine** (3-5 дней)
   - ✅ Протестировать chunking, embeddings, search
   - ⏳ Добавить PDF парсер (PyPDF2 или pdfplumber)
   - ⏳ Cross-encoder reranking (опционально, можно после MVP)
   - ⏳ Pytest тесты + метрики (Precision@5, NDCG)

2. **Скачать и проиндексировать медицинские документы** (2-3 дня)
   - Топ-20 клинических рекомендаций (кардиология, неврология, терапия)
   - Запустить ingestion pipeline
   - Проверить качество поиска на тестовых запросах

3. **Создать FastAPI endpoints** (5-7 дней)
   - `POST /api/v1/search` — RAG-поиск
   - `POST /api/v1/auth/register` — регистрация врача
   - `POST /api/v1/auth/login` — авторизация (JWT)
   - `GET /api/v1/health` — health check
   - Интеграция с RAG Engine, PostgreSQL

4. **Разработать Telegram-бот** (5-7 дней)
   - Авторизация (ФИО, специальность, регион)
   - Команда `/start` — приветствие, инструкции
   - Команда `/search <query>` — RAG-поиск
   - Отображение результатов (источник, уровень доказательности, ссылка)
   - История запросов (сохранение в PostgreSQL)

5. **Деплой на VDS** (1-2 дня)
   - Docker Compose на VDS (DigitalOcean, Hetzner, Selectel)
   - HTTPS (Let's Encrypt)
   - Мониторинг (базовый: логи, uptime)

6. **Тестирование с 5-10 врачами** (1 неделя параллельно)
   - Собрать feedback (что работает, что не работает)
   - Метрики: количество запросов, средняя оценка, retention
   - Итерация на основе feedback

**Критерий успеха MVP:**
- ✅ 10+ активных пользователей (врачей)
- ✅ 100+ запросов за неделю
- ✅ <2s среднее время ответа RAG
- ✅ >4.0/5.0 средняя оценка качества ответов

**Timeline:** 3-4 недели (учитывая solo founder)

### 3.2. Roadmap на 3 месяца (MLP — Minimum Lovable Product)

**Месяц 2:**
- Symptom Analyzer (базовый) — интеграция GigaChat для анализа симптомов
- Команда `/analyze <symptoms>` в Telegram-боте
- React frontend (MVP UI: search bar + результаты)
- Расширить базу знаний до 50+ документов

**Месяц 3:**

- Фильтры по специальности, году публикации

- Feedback система (оценка результатов 👍👎)
- Документация для пользователей

**Критерий успеха MLP:**
- 50+ активных пользователей
- 500+ запросов/неделю
- >80% Precision@5
- 3-5 платящих пользователей (Pro tier: 499 руб/месяц)

### 3.3. Стратегия на 6-12 месяцев

**Месяц 4-6: Full Product**
- Multimodal Processor (OCR для анализов)
- Мобильное приложение (PWA или React Native)
- API для сторонних разработчиков
- Интеграция с МИС (пилот с 1 клиникой)

**Месяц 7-12: Scale & B2B**
- Масштабирование (Kubernetes, load balancing)

- Образовательный контент (курс для врачей)

**Критерий успеха (12 месяцев):**
- 200+ активных пользователей (B2C)
- 5-10 корпоративных клиентов (B2B)
- 500k-1M руб MRR
- Break-even или близко к нему

## 4. Монетизация

### 4.1. Рекомендуемая модель: Freemium + B2B

**Free tier:**
- 20 запросов/день
- RAG-поиск по базовым протоколам
- Telegram-бот
- История запросов (7 дней)

**Pro tier (499 руб/месяц):**
- Unlimited запросы
- Symptom Analyzer (AI-диагностика)
- Evidence Evaluator
- Web-интерфейс
- История (90 дней)
- Приоритетная поддержка

**Enterprise tier (от 15k руб/месяц):**
- 100+ врачей: 150 руб/врач/месяц
- Custom база знаний (протоколы клиники)
- Интеграция с МИС
- SLA 99.9%
- Обучение персонала

### 4.2. Unit Economics (прогноз)

**B2C (Pro tier):**
```
ARPU: 499 руб/месяц
Churn: 5% (месячный)
LTV: 499 / 0.05 = ~10k руб

CAC (через content marketing): ~1k руб
LTV:CAC = 10:1 ✅ (отлично)

Расходы на пользователя:
- GigaChat API: ~50 руб/месяц (при 100 запросах)
- Инфраструктура: ~10 руб/месяц (амортизация)
= 60 руб/месяц

Маржа: 499 - 60 = 439 руб/месяц (88%)
```

**B2B (Enterprise):**
```
Клиника 100 врачей × 150 руб = 15k руб/месяц = 180k руб/год

Расходы:
- GigaChat API: ~5k руб/месяц (100k запросов)
- Поддержка: 0.5 FTE (~25k руб/месяц) = 300k/год
= 30k руб/месяц = 360k руб/год

Маржа: 180k - 360k = -180k (убыток на одной клинике)

Break-even: ~2 клиники (по 100 врачей)
Прибыльность: 5+ клиник → 180k×5 - 360k = 540k руб/год
```

**Вывод:** B2C высокомаржинальный, но медленный рост. B2B требует минимум 2-5 клиентов для break-even, но дает recurring revenue и высокий LTV.

**Рекомендация:** Начать с B2C (freemium через Telegram), параллельно строить B2B pipeline (месяц 4-6).

## 5. Риски и митигация

### 5.1. Критические риски

#### Риск 1: Качество RAG недостаточное для реальных клинических кейсов

**Сценарий:**
- Врач запрашивает "протокол лечения острого коронарного синдрома"
- RAG возвращает нерелевантные результаты или пропускает важные секции
- Врач теряет доверие, перестает использовать систему

**Вероятность:** Средняя (40%)  
**Влияние:** Критическое (система бесполезна без качественного поиска)

**Митигация:**
1. **Human-in-the-loop evaluation:**
   - Собрать 100 реальных запросов от врачей
   - Ручная проверка top-5 результатов для каждого запроса
   - Target: Precision@5 > 80%

2. **Cross-encoder reranking:**
   - Добавить на второй стадии (top-10 → top-3)
   - Модель: cross-encoder/ms-marco-MiniLM-L-12-v2 (русифицированный)
   - Ожидаемое улучшение: +5-10% Precision@5

3. **A/B тесты разных chunking стратегий:**
   - Semantic (текущий) vs Fixed-size vs Recursive
   - Метрики: Precision@5, NDCG, user ratings

4. **Continuous improvement:**
   - Feedback система (👍👎 для каждого результата)
   - Retrain embeddings на собранных позитивных примерах

**Contingency plan:** Если Precision@5 < 70% после всех улучшений — pivot на Evidence Evaluator (оценка медицинских утверждений) вместо поиска.

#### Риск 2: GigaChat API нестабилен / медленный

**Сценарий:**
- GigaChat API падает или превышает rate limits
- Symptom Analyzer не работает
- Пользователи получают ошибки

**Вероятность:** Средняя (30%)  
**Влияние:** Высокое (функционал недоступен)

**Митигация:**
1. **Fallback на Claude API:**
   - Автоматическое переключение при ошибке GigaChat
   - Retry logic: 3 попытки с exponential backoff (1s, 2s, 4s)
   - Мониторинг uptime GigaChat (alert при downtime >5 минут)

2. **Кэширование популярных запросов:**
   - Redis TTL 1 час для частых symptom analysis
   - Пример: "головная боль + тошнота" → кэшируем ответ
   - Ожидаемый hit rate: 20-30% (снижение нагрузки на API)

3. **Rate limiting на клиентской стороне:**
   - 5 запросов/минуту на пользователя (предотвращает превышение лимитов)
   - Graceful degradation: "Превышен лимит, повторите через 1 минуту"

4. **Мониторинг и алерты:**
   - PagerDuty / Opsgenie для критических ошибок
   - Slack notifications для API downtime

**Contingency plan:** Если GigaChat недоступен >2 дней — временно отключить Symptom Analyzer, оставить только RAG-поиск.

#### Риск 3: Врачи не доверяют AI-рекомендациям

**Сценарий:**
- Врач видит рекомендацию от AI, но не доверяет
- Не использует систему, т.к. боится медико-правовой ответственности
- Негативные отзывы ("AI может ошибаться, опасно для пациентов")

**Вероятность:** Высокая (60%)  
**Влияние:** Критическое (low adoption, high churn)

**Митигация:**
1. **Всегда показывать источник:**
   - Ссылка на документ (КР Минздрав РФ, номер, год)
   - Номер страницы / секция в документе
   - Уровень доказательности (A/B/C/D/E)

2. **Disclaimers на каждом ответе:**
   ```
   ⚠️ Данная информация носит справочный характер и не заменяет 
   консультацию врача. Требуется профессиональная диагностика и 
   назначение лечения специалистом.
   ```

3. **Позиционирование:**
   - НЕ "AI-врач", НЕ "автоматическая диагностика"
   - ДА "информационная система", "помощник для поиска протоколов"
   - Messaging: "Система помогает найти рекомендации, решение принимает врач"

4. **Trust building:**
   - Testimonials от практикующих врачей

## 7. Технические рекомендации

### 7.1. Архитектурные улучшения

#### Приоритет 1: Cross-encoder reranking (месяц 2)

**Проблема:** Базовый reranking (cosine similarity × boosts) недостаточно точный.

**Решение:**
- Добавить cross-encoder на второй стадии:
  - Stage 1: Semantic search (ChromaDB) → top-10
  - Stage 2: Cross-encoder reranking → top-3
- Модель: `cross-encoder/ms-marco-MiniLM-L-12-v2` (русифицированный)
- Ожидаемый прирост: +5-10% Precision@5

**Реализация:**
```python
from sentence_transformers import CrossEncoder

cross_encoder = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-12-v2')

def rerank(query: str, candidates: List[str]) -> List[Tuple[int, float]]:
    pairs = [[query, candidate] for candidate in candidates]
    scores = cross_encoder.predict(pairs)
    return sorted(enumerate(scores), key=lambda x: x[1], reverse=True)
```

#### Приоритет 2: Query expansion (месяц 3)

**Проблема:** Врачи используют разные термины для одного понятия ("ОКС" vs "острый коронарный синдром").

**Решение:**
- Автоматическое расширение запроса через синонимы и аббревиатуры
- Медицинский тезаурус (MeSH на русском, собственный словарь)
- Пример: "ОКС" → ["острый коронарный синдром", "ОКС", "ACS"]

#### Приорит 3: Hybrid search (месяц 4-6)

**Проблема:** Semantic search плохо работает с точными совпадениями (номера протоколов, коды МКБ).

**Решение:**
- Hybrid search: semantic (ChromaDB) + keyword (PostgreSQL full-text search)
- Взвешенная комбинация: 0.7 × semantic + 0.3 × keyword
- Используется pgvector extension в PostgreSQL

### 7.2. Оптимизация производительности

#### Latency targets

| Операция | Target (p95) | Текущее (оценка) | Оптимизация |
|----------|--------------|------------------|-------------|
| Embedding query | <100ms | ~100ms (CPU) | GPU inference / OpenAI embeddings API |
| Semantic search | <200ms | ~150ms | Индексирование ChromaDB |
| Cross-encoder reranking | <300ms | N/A | Batch processing |
| Total RAG pipeline | <500ms | ~450ms | ✅ |
| GigaChat API call | <5s | ~3-8s | Кэширование, fallback |

#### Масштабируемость

**Текущие ограничения:**
- ChromaDB: до 10k документов (достаточно для MVP)
- PostgreSQL: до 100k пользователей (достаточно)
- Redis: до 100 RPS (достаточно)

**Узкие места при масштабировании:**
1. **Embedding generation** (CPU bottleneck)
   - Решение: GPU inference (NVIDIA T4, ~10x speedup) или OpenAI embeddings API
2. **ChromaDB не для high-load** (>100 RPS)
   - Решение: миграция на Qdrant (при росте >1000 пользователей)
3. **GigaChat rate limits** (50 req/hour на free tier)
   - Решение: платный план или fallback на Claude API

- Блог-посты = долгосрочный актив (SEO трафик годами)

#### 5. Построить B2B pipeline для корпоративных клиентов (приоритет P2)

**Timeline:** Месяц 5-6

**Действия:**
- Собрать список 50 клиник (50-200 врачей)
- Cold outreach (email, LinkedIn) к главным врачам
- Подготовить case study (результаты пилота с 1 клиникой)
- Партнерство с интеграторами МИС

**Цель:**
- 3-5 корпоративных клиентов, 500k руб MRR

**Почему это критично:**
- B2B = высокий LTV (180k руб/год на клинику)
- Recurring revenue (предсказуемая выручка)
- Масштабируемость (1 сделка = 100 врачей vs 100 B2C продаж)

### 9.3. Что НЕ делать (anti-priorities)

1. ❌ **Не строить web-интерфейс до MVP**
   - Telegram-бот достаточен для валидации гипотез
   - Frontend можно добавить после feedback от 50+ пользователей

2. ❌ **Не добавлять multimodal (OCR) до MLP**
   - Сложная функция (требует отдельной модели, валидации)
   - Низкий приоритет (врачи сначала хотят базовый поиск)

3. ❌ **Не тратить время на perfect code**
   - MVP должен быть "работающим", не "идеальным"
   - Рефакторинг можно сделать после traction

4. ❌ **Не искать инвестиции до traction**
   - Pre-seed без пользователей = низкая оценка (5-10M руб)
   - Сначала доказать product-market fit, потом привлекать

5. ❌ **Не пытаться делать всё сразу**
   - Focus на 1 key metric: активные пользователи (DAU)
   - Остальное (frontend, multimodal, mobile) — потом
